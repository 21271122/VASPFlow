# VASPFlow 开发路线图

> 文档状态：Draft v0.2  
> 更新日期：2026-09-09  
> 当前产品基线：`dsh-vaspflow@0.2.4`  
> 面向对象：产品负责人、VASP 工作流设计者、插件开发者与未来贡献者

---

## 1. 产品目标

VASPFlow 的目标不是让大模型替代科研判断，也不是做一组互不相干的 VASP 脚本。它要成为一个**可信、可追溯、可观察、原位工作的 VASP 研究工作台**：

1. 把重复、成熟、可验证的工作交给自动化工具；
2. 让 LLM 理解人的意图、编排工具、解释证据并组织项目工作；
3. 让任务、数据、图像、文件和结论在 Agent 前端原位呈现；
4. 让每一项结论都能追溯到输入文件、计算输出和确定性规则，而不是模型的猜测。
5. 让用户在 AI 执行工作时看见真实的计划、进展、文件改动和证据，并能在安全节点介入或接管。

一句话定义：

> **用确定性工具保证 VASP 工作流的事实可靠，用 LLM 降低编排和解释成本，用原位可视化与透明执行让过程和结果都可读、可审阅、可复现。**

### 1.1 三条主线

| 主线 | 定义 | LLM 的位置 | 成功标准 |
|---|---|---|---|
| 自动化 | 重复、成熟、规则明确的流程自动完成 | 可调用工具，但不参与规则判定 | 同样输入得到同样输出；能预览、验证、批量执行 |
| 智能化 | LLM 参与非重复但相对成熟的工作流 | 理解需求、选择工具、解释证据、提出下一步 | 建议有证据、有边界、关键写入前需确认 |
| 可视化 | 在 VASPFlow 前端原位查看数据、结论与工作过程 | 提供结构化汇报和执行状态数据，不直接生成页面 | 用户无需在多个工具间搬运常见结果；能理解 AI 已做、正在做和待确认的工作 |

### 1.2 必须同时建设的第四条底座：可信性、可追溯性与可观察性

自动化、智能化、可视化共用同一份任务事实。每个任务至少需要保留：

- 输入来源、模板、关键参数和实际写入的文件；
- 执行状态、VASP/调度器输出、解析时间和解析器版本；
- 确定性检查的规则、证据与结果；
- LLM 的诊断、建议、用户确认和最终操作；
- 结果图表使用的数据文件、处理参数和单位。
- 工作流的计划、真实操作事件、变更目标、执行结果和中断/确认记录。

这不是额外的“日志功能”，而是 VASPFlow 能被科研使用的基础。没有它，批量结果难以复查，LLM 项目日志会变成不可验证的叙述，图表也无法说明来源；用户也只能相信 AI 的口头汇报，无法观察其工作。

可观察性不等于暴露模型内部思考，也不等于用模拟鼠标或逐字打字制造“AI 正在忙”的感觉。它只呈现真实发生的计划、文件操作、校验、产物和可回链证据。

## 2. 当前基线与判断

截至 `0.2.4`，VASPFlow 已经具备正确的基础架构：前端面板、宿主 Node 数据服务与 VASP Agent 预设共享同一数据层。它不是单纯的提示词集合。

已具备的能力包括：

- 项目目录扫描、任务树/表、任务状态初步识别；
- OUTCAR/OSZICAR 解析、收敛曲线、3D 结构和文件原位浏览；
- 批量输入构建、dry-run 预览、POTCAR/POSCAR 顺序检查、Selective dynamics 保护、批次一致性检查；
- INCAR 和 OUTCAR 的确定性解析/校验；
- 通过 VASP Agent 预设让 LLM 调用 `vasp_*` 工具，而非临时猜测或手写解析脚本。

### 2.1 当前最强的部分

- **确定性优先。** SD 旗标、POTCAR 顺序、INCAR 基本矛盾等关键问题交给工具，而不是模型猜。
- **人机共用数据层。** 面板和 Agent 读取同一任务状态，避免“模型说的”和“图上显示的”不一致。
- **批量构建前有预览和校验。** 这是科研自动化中比“能写文件”更重要的安全设计。

### 2.2 当前主要缺口

1. 任务状态仍偏“目录扫描结果”，尚未形成统一的任务生命周期和批量巡检能力；
2. 缺少 DOS、COHP/LOBSTER、ZPE 等结果的标准解析与原位图表；
3. 缺少统一的任务台账、事件记录和可审阅的 LLM 汇报载体；
4. 失败诊断目前尚未形成“规则取证 → LLM 解释 → 用户确认修复”的闭环；
5. AIMD、调度器和长任务管理尚未进入产品范围。

## 3. 产品边界与设计原则

### 3.1 不做什么

- 不宣称自动判断一个计算在科学上“正确”；
- 不让 LLM 在没有工具证据时判断收敛、错误类型或物理结论；
- 不默认覆盖 `CONTCAR`、`WAVECAR`、`CHGCAR` 等关键文件；
- 不在未确认模板、提交脚本、任务路径时批量写入或提交计算；
- 不试图取代 VESTA、pymatgen、VASPKIT、LOBSTER 等所有专业软件的全部能力。

VASPFlow 的定位是将研究中最高频、最容易出错、最需要协调的部分原位化；少数深度专业操作仍允许导出到专业工具。

### 3.2 统一原则

1. **确定性优先。** 数值计算、文件判定、状态识别均由可测试代码完成。
2. **先预览后写入。** 任何批量构建先支持 dry-run；涉及提交、覆盖、续算时必须明确确认。
3. **证据先于叙述。** LLM 的结论必须引用任务、文件、规则或图表中的证据。
4. **结构化输出先于自然语言。** 工具先返回稳定 JSON；自然语言和面板只是对该数据的呈现。
5. **渐进支持。** 每类任务先支持一条高频、边界清晰的标准工作流，再扩展变体。
6. **单任务可用，批量更有价值。** 新功能应同时考虑批量筛选、对比、导出与异常汇总。
7. **任务是实验单元，不是文件夹。** 界面优先呈现体系、构型、吸附物种、位点、参数与状态；文件树是核查证据，不是批量工作的主叙事。
8. **视觉状态必须由事实驱动。** “进行中”“已校验”“失败”等状态只能来自实际操作事件和确定性检查，不能由 LLM 或动画推断。
9. **在安全检查点交接。** 正常批量工作可安静完成；涉及写入、覆盖、提交或不确定性时，用户可在任务边界确认、暂停或接管。

## 4. 总体架构演进

当前的“前端面板 ↔ 宿主数据服务 ↔ Agent 工具”结构保持不变。后续新增功能应作为共享数据服务和稳定工具契约的扩展，不应把核心解析逻辑塞进提示词或前端组件。

```text
VASP / LOBSTER / 调度器文件
          │
          ▼
解析器与确定性检查器 ──► 任务记录 / 构建计划 / 工作流运行 / 操作事件 / 证据记录
          │                                  │
          │                                  ├──► Agent 工具（结构化 JSON）
          │                                  ├──► 原位图表、执行工作台与报告卡片
          │                                  └──► 项目日志与可导出报告
          ▼
输入构建、预览、校验、提交前确认
```

### 4.1 建议逐步建立的六类核心数据契约

这些是内部 JSON 契约，不要求一开始就做成复杂数据库；早期可由项目目录中的轻量 JSON 记录实现。

| 契约 | 用途 | 最小字段 |
|---|---|---|
| `TaskRecord` | 单个计算实验单元的事实状态 | 路径、体系/构型/位点等语义标识、任务类型、状态、关键输入/输出摘要、更新时间 |
| `BuildPlan` | 写入前可审阅的变更清单 | 来源与目标路径、计划创建/复制/链接/改写的文件、参数差异、覆盖风险、源文件哈希、dry-run 检查结果 |
| `WorkflowRun` | 一次批量构建/处理的运行状态 | 运行 ID、意图、关联计划、目标任务、阶段、进度、操作者、用户确认、最终结果 |
| `OperationEvent` | 一条真实发生的操作或检查 | 序号、时间、任务、操作类型、来源/目标、结果、严重级别、证据引用 |
| `EvidenceRecord` | 判定和诊断的依据 | 规则 ID、文件、行/文本证据、严重级别、结论 |
| `ReportCard` | LLM 向面板汇报的结构化内容 | 标题、摘要、指标、表格、图表引用、文件引用、下一步操作 |

`BuildPlan` 与 `WorkflowRun` 分别回答“准备做什么”和“实际做了什么”；`OperationEvent` 让前端能以真实事件呈现批量工作过程。早期不必引入复杂数据库，可由项目目录中的轻量 JSON 记录实现。

`ReportCard` 是“LLM 汇报面板”的关键，但它是任务完成后的结构化总结，不应承担实时运行状态。模型只能填写受校验的卡片数据；前端负责把表格、曲线、目录树、警告和按钮画出来。不要让模型直接输出 HTML 或任意页面代码。

### 4.2 Agent 工具契约收敛（0.3 实施项）

当前 12 个 `vasp_*` 工具把同一对象的“状态、文件列表、文件预览”拆成多次调用，也把“结构源盘点、模板候选”和文件解析拆得过细。这增加了 LLM 的选工具成本、临时 `taskId` 依赖和漏掉关键步骤的概率；它不增加确定性能力。

0.3 将 Agent 可见工具收敛为 7 个。每个工具仍返回结构化 JSON，并保留顶层 `error`；面板 HTTP 接口不受影响。INCAR、OUTCAR 等任务文件的确定性解析由巡检、输入检查和扫描器内部完成，不再单独暴露“先读全文、再分析文本”的 Agent 工具。

| 保留/新增工具 | 来源 | 最小职责与输入 |
|---|---|---|
| `vasp_scan` | 保留 | `rootPath`：扫描项目，刷新共享任务记录 |
| `vasp_inspect_task` | 新增；合并 `vasp_get_status_detail`、`vasp_task_files`、`vasp_read_file` | `rootPath` + `relPath` 稳定定位一个任务；`include` 选择状态、目录文件清单和一个文件预览；预览使用 `file: { name, part: head/tail/previous, bytes, cursor }`，不暴露字节偏移给用户或 LLM |
| `vasp_convergence` | 保留 | `rootPath` + `relPath` 稳定定位任务，返回能量/最大力序列；不依赖临时 `taskId` |
| `vasp_structure_scene` | 保留 | `rootPath` + `relPath` 定位任务，将 POSCAR/CONTCAR 转为晶胞、原子、键和摘要，供原位 3D 视图；不替代读取原始文件 |
| `vasp_discover_inputs` | 新增；合并 `vasp_src_inspect`、`vasp_scan_templates` | `rootPath`、`maxDepth`、`include`：一次返回结构源体检与模板候选；只发现和报告，绝不替用户选择模板或提交脚本 |
| `vasp_build_inputs` | 保留 | 批量构建；仍要求先 dry-run，再执行写入 |
| `vasp_check_inputs` | 保留 | 按指定规则检查输入，并返回实际同步到任务面板的数量；未关联不能被描述为面板已更新 |

实施顺序与兼容策略：

1. 先新增三个合并工具，并以回归测试确认它们覆盖旧工具能力；
2. 更新 VASP Agent 预设和随附技能，只向新会话注册 7 个工具；
3. 旧工具实现可暂时作为内部复用函数保留，但不再出现在 Agent 工具目录；
4. 用“扫描 → 单任务核查 → dry-run 构建 → 输入检查 → 结果分析”的完整工作流验收；
5. 仅在 0.3 开发测试和实际样例验证后，才随新的 npm 版本公开发布。

验收标准：同一任务的状态、文件与预览可由一次 `vasp_inspect_task` 获得；源文件与模板候选可由一次 `vasp_discover_inputs` 获得；任务目录内的 INCAR/OUTCAR 分析不需要把全文搬入 Agent 上下文，仍能由巡检、输入检查和扫描器返回结构化证据。工具数量减少不得降低状态判定、输入检查和文件预览的可追溯性。

## 5. 开发路线图

版本号代表能力阶段，不承诺日历时间。单人开发应以前一阶段的验收完成为下一阶段的入口，避免同时铺开 DOS、COHP、AIMD 等多个重工作流。

### 阶段 A：0.2.x — 稳定基础与样例验收

**目标：** 确保新用户能安装、现有工具能在真实小项目中稳定工作，并建立后续功能的回归基线。

| 工作项 | 内容 | 验收标准 |
|---|---|---|
| 发布与安装 | 维护 npm 一键安装、预设安装、升级和重装说明 | 空白环境可安装插件与预设；旧预设不会被静默覆盖 |
| 回归样例库 | 收集脱敏的小型结构优化、失败 OUTCAR、异常 POSCAR/POTCAR 案例 | 每个已修复 bug 都有可自动运行的回归样例 |
| 工具契约 | 固化工具输入/输出 schema 与错误格式 | 任意工具失败都返回可识别错误，不破坏其他批量任务 |
| 可视化稳定性 | 验证任务列表、收敛图、结构、文件预览的联动 | Agent 与面板显示的任务数、能量和状态一致 |
| 可观察构建基线 | 为现有批量输入构建补齐 `BuildPlan`、`WorkflowRun` 与 `OperationEvent` | dry-run 能列出每个任务的来源、目标、参数差异、检查和覆盖风险；真实写入可回链到操作事件 |

**本阶段不新增大型任务类型，也不承诺完整的实时工作台。** 它的产物是后续版本不会反复打碎的可靠地基：先让“计划—执行—证据”能被记录和验证，再将它画成界面。

### 阶段 B：0.3 — 批量任务巡检、透明构建与项目任务台账

**目标：** 解决用户每天最迫切的问题：当前有哪些计算、哪些成功、哪些卡住、哪些需要我处理；并让批量构建的过程可观察、可核查、可在安全节点交接。

#### B1. 统一任务状态模型

状态不是对任务是否“可以提交”或“科学上正确”的承诺，而是对当前文件系统中可观测事实的分类。尤其不能把“发现了若干输入文件”称为 `READY`：文件是否足够、模板是否适用于当前课题、是否可以消耗计算资源，仍需要用户的工作流判断。

> 实现状态（2026-09-10，开发测试态）：B1-0 至 B1-6 已落入插件源码并通过本地回归测试；尚未发布 npm。首版状态扫描、详情与输入检查均只读取文件，不会提交作业或改写 VASP 输入。

状态分为三个层次，但用户在主界面只需要看前两层：

1. **目录类型**：普通目录或 VASP 任务目录；
2. **任务分流状态**：五个互斥的主状态，每个 VASP 任务只能有一个；
3. **状态原因与输入检查结果**：只在任务详情和 Agent 报告中展开，不能反推为“可提交”。

##### B1.1 目录类型与五个任务状态

| 层次 | 代码 | 面向用户的文字 | 颜色 | 严格含义 |
|---|---|---|---|---|
| 目录类型 | `ORDINARY_DIRECTORY` | 普通目录 | 无 | 不同时存在 `POSCAR`、`INCAR`、`KPOINTS`、`POTCAR`；不参加 VASP 状态检测 |
| 目录类型 | `VASP_TASK_DIRECTORY` | VASP 任务目录 | 无 | 标准单任务目录同时存在四个输入文件；不据此断言任务可提交或科学上正确 |
| 任务状态 | `NO_OUTPUT_EVIDENCE` | 未发现计算输出 | 黄 | VASP 任务目录中未发现 `OUTCAR`、`vasprun.xml`、`OSZICAR` 或有效 Slurm 输出日志 |
| 任务状态 | `TASK_COMPLETED` | 任务完成 | 绿 | 有正常结束标记，且通过该任务类型的确定性完成判据；详情显示具体为“结构优化收敛”“频率结果完整”“轨迹完成”等 |
| 任务状态 | `ERROR_DETECTED` | 检测到错误 | 红 | 当前一次计算的相关输出中匹配确定性错误签名，或已正常结束但触发任务类型明确的失败判据（如结构优化耗尽 `NSW` 仍未离子收敛） |
| 任务状态 | `RUNNING` | 正在运行 | 蓝 | 有调度器运行证据；或连续两次扫描确认相关输出仍在增长/更新 |
| 任务状态 | `UNKNOWN` | 待检查 | 灰 | 除以上情况外：未结束但未证明仍在运行、正常结束但无法验证、证据冲突或解析失败 |

标准单任务目录必须同时存在 `POSCAR + INCAR + KPOINTS + POTCAR` 才被识别为 `VASP_TASK_DIRECTORY`。缺少任一文件就是普通目录，不进入 VASP 任务状态模型。

NEB 是唯一明确例外：它是一个复合 VASP 任务。父目录必须有 `INCAR`、`KPOINTS`、`POTCAR`，且 `INCAR` 中存在正整数 `IMAGES`；同时包含按编号命名的 image 子目录，子目录中应有对应的 `POSCAR`。标准 VASP NEB 将共享输入置于父目录、将各 image 的 POSCAR 和输出置于子目录，因此不能强行套用“同目录四文件”的单任务规则。

`RUNNING` 不能由“存在输出文件”推断。没有调度器查询时，扫描器必须比较连续两次扫描中 `OUTCAR`、`OSZICAR` 或有效 Slurm 日志的大小/修改时间；只有出现增长才可标蓝。单次看到未结束输出、输出停滞、正常结束但缺少适用判据、解析器不能读出结束标记，均进入灰色 `UNKNOWN`，并在详情显示原因与最后更新时间。

带有 `slurm` 的文件名可作为输出日志候选，但 `slurm.sh`、`.sbatch` 等提交脚本必须排除；文件名本身也不能证明调度器仍在运行。若成功与错误证据无法确认属于同一次计算，状态固定为 `UNKNOWN`，不得武断地覆盖为绿或红。

##### B1.2 常见任务类型与完成判据

“任务完成”是统一状态；“收敛”只适用于确有收敛目标的任务。任务类型应先由 INCAR、KPOINTS 与目录结构识别，再选择对应判据。

| 首版类型 | 初步识别 | `TASK_COMPLETED` 判据 | 不纳入完成判据的事项 |
|---|---|---|---|
| 静态单点 / SCF | 通常 `NSW=0` 且非频率、非 MD、非 NEB | OUTCAR/vasprun.xml 有正常结束标记；未命中电子自洽失败或致命错误签名 | 能量、K 点、截断能是否达到用户所需精度 |
| DOS / PDOS / 电荷密度 / ELF / 静态 COHP 前置计算 | 由静态任务加 `LORBIT`、`LCHARG`、`LAECHG` 等输出意图识别 | 静态 SCF 判据通过；若用户声明需要某输出，再确认 DOSCAR、CHGCAR、ELFCAR 等目标文件存在 | DOS/电荷/ELF/COHP 图或数值是否具有科学解释；COHP 的 LOBSTER 后处理另有独立工作流状态 |
| 能带 | 线模式 KPOINTS 或 `ICHARG=11` 等非自洽能带特征 | 正常结束，未命中电子自洽或致命错误；若用户声明能带任务，确认 EIGENVAL/vasprun.xml 等目标输出存在 | 路径是否适合该晶体、能带图是否有物理意义 |
| 结构优化 / 晶胞优化 | 常见 `IBRION=1/2/3` 且 `NSW>0`，非 NEB | 正常结束，且出现 `reached required accuracy` 等离子优化收敛证据；必要时按 `EDIFFG` 校验 | 最终结构是否为所需构型或全局最低能 |
| 频率 / ZPE | `IBRION=5/6/7/8` | 正常结束，且 OUTCAR 中频率/振动模式区块可完整解析 | 虚频不使任务标红；它是物理稳定性与后处理质量警告 |
| AIMD | `IBRION=0` 且 `NSW>0` | 正常结束，且已完成目标轨迹步数（以 `NSW` 和实际输出步数交叉检查） | 温度漂移、能量漂移、轨迹是否已充分采样；它们是质量诊断，不是“收敛” |
| NEB / CI-NEB | 父目录的 `IMAGES>0` 加 image 目录结构 | 所有必需 image 均有一致的完成证据，且 NEB 专项解析确认链力/收敛判据满足 | 原始 DFT 原子力不能替代 NEB 链力；过渡态是否只有一个虚频属于后续验证 |

静态计算在本路线图中指**不进行离子步进的电子结构计算**：通常是单点 SCF，也包括在已收敛电荷密度上进行的 DOS、能带、CHGCAR/ELFCAR 等后处理前置计算。它不是“什么都不检查”的泛称。VASP 中 `NSW=0` 是默认的无离子步设置；能带线模式通常应冻结已收敛电荷密度（如 `ICHARG=11`）。

结构优化、频率和 AIMD 分别由不同的 `IBRION` / `NSW` 模式定义；频率结果写入 OUTCAR，AIMD 的 `NSW` 是轨迹步数而不是收敛门槛。NEB 的共享输入位于父目录、image 输出位于子目录，且需检查 NEB 专用的链力，不能复用普通结构优化的原子力判据。参考：[VASP IBRION](https://vasp.at/wiki/IBRION)、[NSW](https://vasp.at/wiki/index.php/NSW)、[KPOINTS 能带说明](https://vasp.at/wiki/KPOINTS)、[NEB](https://vasp.at/wiki/Nudged_elastic_bands)。

##### B1.3 错误签名库的边界

`ERROR_DETECTED` 由带版本和回归样例的确定性失败规则触发。首版优先覆盖数值/电子错误（如 `EDDDAV`、`BRMIX`、`Sub-Space-Matrix is not hermitian`）、进程异常（如 `Segmentation fault`、`forrtl: severe`）、Slurm 资源/调度错误（如 `OUT_OF_MEMORY`、`oom-kill`、`DUE TO TIME LIMIT`、`CANCELLED`），以及“已正常结束但明确未满足该任务终止要求”的规则，例如结构优化达到 `NSW` 仍未出现离子收敛标记。每条规则必须记录匹配文件、行号或尾部片段、类别和严重级别；模糊的 `error` 字样或历史日志不能直接标红。

特别地，`aborting loop because EDIFF is reached` 是电子最小化达到 `EDIFF` 判据的正向证据，不是错误签名；对于结构优化，它不能替代离子优化的 `reached required accuracy`。现有扫描器将这一文字误判为错误，B1-0 必须先用回归样例锁定并修复。参考：[VASP 官方论坛说明](https://vasp.at/forum/viewtopic.php?t=19374)。

##### B1.4 输入检查结果（独立维度）

| 检查代码 | 面向用户的文字 | 含义 |
|---|---|---|
| `NOT_REQUESTED` | 未指定检查规则 | 用户尚未声明任务类型或模板，系统不猜测“应有哪些文件” |
| `NOT_CHECKED` | 尚未检查 | 已选规则但未执行确定性检查 |
| `PASS` | 通过指定规则检查 | 仅表示符合该规则版本的已检查项，不表示科学上必然正确或可直接提交 |
| `WARN` | 发现需注意项 | 规则允许继续，但存在缺失、差异或需人工确认的信息 |
| `FAIL` | 未通过指定规则检查 | 已有确定性规则证据表明不符合所选工作流要求 |

输入检查必须携带 `profileId`、`profileVersion`、实际检查的文件、未检查项和证据。界面固定显示“通过 *某规则* 检查”，禁止简化成“已就绪”或“可提交”。

##### B1.5 状态记录与兼容策略

新的 `TaskRecord` 应把主状态记录为 `{ code, label, evidence, observedAt }`，并单列 `inputCheck`。现有 `status: finished/error/unknown` 在 0.3 迁移期保留为兼容字段；新面板和 Agent 只以新状态对象为准。每次扫描都要同时返回状态、理由和最小证据引用，不能仅返回一个枚举字符串。

##### B1.6 面板呈现与用户操作

沿用现有任务树和表格中的**状态圆点**，因为它在大量任务中足够紧凑；但圆点不能成为唯一表达。应抽成一个全局统一的 `StatusBadge`，由任务树、任务表、详情标题、筛选器和后续任务实验板共同使用：

| 场景 | 呈现方式 | 用户可获得的信息 |
|---|---|---|
| 任务树 | 普通目录用文件夹图标；VASP 任务用圆点 + 图标形状 + 悬浮文字 | 快速区分目录类型；悬浮显示任务状态、理由与最近观察时间 |
| 任务表 | 带文字的状态徽标 | 状态名称、输入检查结果、最近观察时间；支持按状态筛选和排序 |
| 任务详情标题 | 状态徽标 + 一句理由 | 例如“待检查：OUTCAR 已 18 小时未更新，未见正常结束标记” |
| 状态汇总条 | 可点击的统计筛选项 | 例如“任务完成 12”“正在运行 3”“待检查 4” |
| 证据区 | 文件链接与短片段 | 让用户直接打开 OUTCAR、OSZICAR 或输入检查报告核对 |

推荐的视觉语义是：普通目录使用中性文件夹；黄色文件图标表示“未发现计算输出”；绿勾表示“任务完成”；红叉表示“检测到错误”；蓝色活动环表示“正在运行”；灰色问号表示“待检查”。色彩必须与图标、文字共同出现，不能只靠颜色，也不能为没有真实事件的任务播放动画。

B1 不重做文件资源管理器。现有树视图继续承担按路径寻找任务的作用；表格承担筛选、排序和批量巡检；选中一个任务后，详情区首先显示“状态与证据”，其后才是收敛图、结构和文件。阶段 B 的后续“任务实验板”再提供按体系、构型和参数分组的主视图。

##### B1.7 Agent 与面板的协作

Agent 需要配套的确定性状态检查工具，但它不拥有状态判断权。推荐分工如下：

| 组件 | 责任 |
|---|---|
| `vasp_scan` | 项目级发现与刷新：识别候选任务、生成并写入统一状态记录，供面板和 Agent 共用 |
| `vasp_inspect_task`（新增） | 对一个已扫描任务做深度核查，输入 `rootPath + relPath`，返回状态、理由、文件时间、错误/完成证据、目录文件与所需预览；不写入输入文件 |
| `vasp_check_inputs` | 仅在用户指定模板/任务类型后执行输入规则检查，返回独立的 `inputCheck`，不把结果改写为“可提交” |
| LLM | 调用工具、按状态分组、解释证据、指出哪些判断必须由用户完成；不得从文件名或经验自行改写状态 |

交互路径保持现有低摩擦方式：用户在面板点击“刷新”得到当前状态；点击任务后可选择“分析此任务”，面板将状态、理由和证据摘要带入对话；Agent 先调用 `vasp_scan`，需要解释单项时再调用 `vasp_inspect_task`，最后给出证据化说明。Agent 工具完成扫描或核查后，应更新同一个 TaskStore 并递增版本号，现有面板轮询机制即可自动刷新，不需要两套状态来源。

`taskId` 是当前 DSH 进程内 TaskStore 分配的临时数字索引，重启后不保证稳定，仅适合面板内部请求。Agent 工具必须使用稳定的 `rootPath + relPath`：前者定位项目，后者定位其中一个任务；只传项目目录无法唯一指定某个任务。

首版不在面板中提供“让 Agent 直接修改状态”的按钮，也不让 Agent 静默修复任务。面板的写入性操作仍遵守后续的计划—确认—执行流程。

##### B1.8 实施顺序与验收

| 步骤 | 改动范围 | 完成标志 |
|---|---|---|
| B1-0：状态样例 | 建立普通目录、四输入单任务目录、NEB 复合目录、五类任务状态和五类输入检查结果的最小脱敏目录样例；包含 `aborting loop because EDIFF is reached` 的正向电子收敛样例 | 每个样例都有预期状态、理由和证据文件；不依赖 LLM |
| B1-1：状态判定器 | 在宿主侧将目录发现与状态判定分离；输入是文件清单/解析摘要，输出是新的状态对象 | 单元测试覆盖每个状态及“证据不足”分支；分类函数没有文件写入权限 |
| B1-2：扫描契约 | 扩展 `vasp_scan` 和 TaskStore，使候选输入目录也能被记录；保留旧 `status` 字段作为兼容映射 | 面板、工具返回和 TaskStore 对同一目录给出相同新状态 |
| B1-3：深度核查工具 | 新增 `vasp_inspect_task`，以 `rootPath + relPath` 查询单项；输出完整理由、时间、证据与需要的文件预览 | Agent 能回答“为什么是这个状态”，而不是仅复述标签 |

| B1-5：面板迁移 | 将当前树点、表格标签、详情页、筛选器统一为 `StatusBadge`；详情页新增“状态与证据”首屏 | 颜色、图标、文字和筛选结果完全来自同一状态对象 |
| B1-6：Agent 协议与回归 | 更新 VASP Agent 的状态巡检协议，并用混合批次做端到端测试 | Agent 完成一次巡检后，面板自动刷新；报告的每个状态可回链到证据 |

当前代码中的 `scanner.js` 只会将含 `OUTCAR` 或 `vasprun.xml` 的目录作为任务，并只生成 `finished / error / unknown`；B1-1/B1-2 将是这一限制的实质性替换。当前面板的任务树圆点、表格和“分析此任务”入口已经存在，B1-5 应复用它们，避免为状态管理另造一个孤立界面。

#### B1 后续优化：静态状态判定与渐进扫描体验

本节是 B1 首版完成后的**追加优化项**。它不改变 B1 已定义的五个主状态、四输入文件识别规则或“状态与输入检查分离”的原则；它修正两项实现策略：运行状态必须由一次扫描中的静态证据得出，项目扫描则应在不牺牲状态可辨认性的前提下渐进呈现。

##### B1-P1. `RUNNING` 的静态判定

不以“前后两次扫描文件是否变化”作为 `RUNNING` 的前提。每次扫描均应独立读取当前目录的输入、输出和日志，根据本次可见的终止证据作出判定；缓存只可复用未变化文件的解析结果，不能成为状态判断的证据。

对已识别的 VASP 任务目录，按如下顺序分类：

1. **任务完成（绿）**：发现正常结束标记，且该任务类型的完成目标已达到；
2. **检测到错误（红）**：发现能够证明本次执行已被中断的致命错误、调度器终止证据，或已正常结束但触发任务类型明确的失败判据；
3. **正在运行（蓝）**：已经存在计算输出，但尚未达到该任务的完成目标，也未发现任务终止或致命错误的证据；
4. **待检查（灰）**：输出不可解析、不同文件的终止证据彼此冲突，或当前版本尚未为该任务类型定义可验证的完成/失败边界；
5. **未发现计算输出（黄）**：保留原定义。

这里的“正在运行”是面板面向工作流的操作语义：**该任务尚未完成，且当前目录没有显示其已被终止**。它不是对 CPU 或 Slurm 队列状态的物理证明；后续接入 `squeue` / `sacct` 后，可在详情中额外显示“调度器已确认运行”，但不改变纯文件模式下的上述静态分类。

`ZBRENT` 必须按具体文本分级，不能作为无条件的红色错误：

| 可观察情况 | 主状态 | 详情中的证据表达 |
|---|---|---|
| `ZBRENT: can't locate minimum, use default step`，随后出现 `reached required accuracy` | 任务完成 | 完成；附“离子步中出现 ZBRENT 回退警告” |
| 同一条非致命 `ZBRENT`，尚无完成或终止证据 | 正在运行 | 运行中；附警告，建议后续复核离子优化路径 |
| 非致命 `ZBRENT`，但已有正常结束标记、达到 `NSW` 且未达到离子收敛 | 检测到错误 | 未收敛；附 ZBRENT 警告，但不将该警告本身视为错误原因 |
| 明确的致命 ZBRENT 文本，或其后紧跟调度器取消、段错误、内存不足等终止证据 | 检测到错误 | 错误；显示匹配文本和终止文件 |

不同任务类型的“尚未达到完成目标”应严格对应各自的静态判据：结构优化尚无 `reached required accuracy`；有限差分频率尚未完成最后的 `Total: n/n` 位移进度并写出可识别的频率模式；AIMD 实际离子步尚未达到 `NSW`；NEB 尚有 image 未完成或缺少链力收敛证据。静态单点 / SCF 则以电子最小化和正常结束证据为完成目标，不应因为存在 `DOSCAR`、`LORBIT` 或 `NEDOS` 而改变任务意图名称。

结构优化是已定义失败边界的例子：若任务已有正常结束标记、已达到 `NSW`，但仍没有 `reached required accuracy` 或等价离子收敛证据，必须标为“检测到错误：未收敛”，而不是“正在运行”或“待检查”。其他任务类型在尚未定义同等明确的失败边界前，已结束但无法验证完成的情况仍保留为“待检查”。

##### B1-P2. 计算机制与研究意图分离

自动识别只负责识别可由输入确定的**计算机制**，例如静态 SCF、结构优化、AIMD、频率或 NEB。DOS、PDOS、COHP、吸附能等是研究意图或分析工作流，不能仅根据某个 INCAR 标签或某个后处理文件倒推。

因此，未被用户或构建工作流明确标注的 `NSW=0` 任务统一展示为“静态单点 / SCF”；`LORBIT`、`NEDOS`、`LCHARG`、`LELF` 等只作为“可用输出意向”写入详情。`DOSCAR` 是 VASP 的常规输出，`TDOS.dat` 等 VASPKIT 文件又不是普适标准，均不能单独证明任务意图。后续 `BuildPlan` 或用户在任务卡片上的明确选择，才可写入稳定的 `workflowIntent: DOS | COHP | ...`；相应产物文件只用于核验该已声明意图是否得到结果。

##### B1-P3. 广度优先、可辨认的实时项目扫描

项目扫描不采用“立即画出完整树，再慢慢补状态”的方式。用户看到的每一个 VASP 任务状态都必须来自该目录已经完成的一次扫描；未扫描节点不得先显示灰色、蓝色或任何会被误解为判定结果的状态。

扫描器按目录层级广度优先工作，并以有限并发处理同一层级。扫描事件至少包含：

| 事件 | 面板行为 |
|---|---|
| `directory-discovered` | 父目录展开时，为该子目录放置无状态的加载占位项；不展示任务状态圆点 |
| `directory-scanned` | 用实际结果替换占位项：普通目录显示普通文件夹；VASP 任务显示经本次扫描得出的状态徽标 |
| `directory-failed` | 用“无法扫描”项替换占位，显示原因；不能伪装成 VASP 任务错误 |
| `scan-complete` | 结束全局加载提示，状态汇总由“已扫描任务数 / 全部已发现目录数”切换为最终总数 |

例如扫描根目录下的 `A` 时，若 `A/B` 已扫描完而 `A/C` 尚在队列中，用户展开 `A` 后只看到带真实状态的 `B` 和一个“正在检查目录 C”的加载占位。`C` 完成扫描后才替换为真实节点。这一规则使用户能分清“已判定为待检查”和“系统尚未扫描到”两件不同的事。

状态汇总条在扫描未结束时必须写明进度，例如“已扫描 46 个任务，仍在检查 18 个目录”；不得将局部结果当作全项目总数。用户可随时查看已完成扫描的任务，但新一轮扫描开始时，为避免新旧状态混杂，应在任务详情显示本轮扫描时间和扫描批次号。

##### B1-P4. 扫描缓存与 I/O 优化

缓存的目标是减少重复读取，不改变 P1 的单次静态判定。缓存键应只包含会影响结论的事实：四个输入文件、任务类型相关输入、`OUTCAR` / `OSZICAR` / `vasprun.xml` / 有效 Slurm 日志及 NEB image 输出的大小和修改时间。键未变化时可复用 INCAR 摘要、任务类型、尾部解析和已生成的状态证据；任一相关文件变化即重新解析该任务。

实现时优先采用以下最小改动：

1. 一次 `readdir({ withFileTypes: true })` 同时获得文件与目录类型，避免“判断类型一次、读取大小再一次”的重复 `stat`；
2. 不对每个普通目录做 `realpath`、完整 INCAR 解析或输出尾部读取；只有发现四输入文件或 NEB 候选时才进入任务判定；
3. 对任务目录只读取完成判据需要的少数文件，且只读 OUTCAR / Slurm 日志的尾部片段；
4. 将同一层级的目录以受限并发扫描，保持广度优先的事件顺序，避免一次打开过多文件；
5. 取消已被新的“打开项目”操作替代的旧扫描请求，前端只接受最新扫描批次的事件。

##### B1-P5. 文件页：保持交互，改为分块读取

文件页维持当前交互：点击文件即在现有预览窗口中打开，不因为文件名或扩展名改变用户可点击的范围。小文件仍一次加载；大文件改为有位置概念的分块读取，而不是整文件读入内存。

初始预览保留当前“优先显示末尾日志”的习惯，以便查看 OUTCAR 和 Slurm 的最新信息；窗口提供继续读取更早或更晚片段的操作。服务端接口应接受 `offset + length` 并返回实际读取范围、总大小和是否还有前/后续内容；前端将已读取片段缓存于当前预览会话。这样仍是同一个文件预览界面，但不会因大型 OUTCAR、CHGCAR 或二进制内容阻塞后端，也不会把 500 KB 以上内容一次塞入 React 页面。

##### B1-P6. 追加验收

1. 单次扫描中，未完成且未见终止/致命错误的结构优化、频率、AIMD、NEB 分别显示“正在运行”，不依赖前一次扫描；
2. 结构优化正常结束、达到 `NSW` 但未满足离子收敛判据时显示“检测到错误：未收敛”；尚未定义失败边界的其他任务才显示“待检查”，且不误称“正在运行”；
3. `ZBRENT: can't locate minimum, use default step` 不会单独标红；其后有结构优化收敛标记时为“任务完成 + 警告”；
4. 含 `LORBIT` / `NEDOS` 的未声明静态任务仍显示“静态单点 / SCF”，详情仅提示可用输出意向；
5. 扫描中的树不会提前显示未判定任务状态；展开父目录时，已扫描子目录和未扫描加载占位可明确区分；
6. 对同一未变化项目重复扫描时，不重复读取未变化任务的 OUTCAR 尾部；修改一个任务的 OSZICAR 后，只重新解析该任务；
7. 含大量目录和大输出文件的项目中，文件预览请求不会被整项目扫描长期阻塞；大文件预览可按块继续读取。

##### B1-P7. 输入检查的面板入口（首版）

输入检查是独立于“计算状态”的一次**显式只读操作**。扫描不会自动将任务标记为通过，也不能因任务类型识别结果而静默选择规则；用户始终能看到并修改本次采用的规则。

首版入口放在已选 VASP 任务的详情标题中，按钮文字为“输入检查”。点击后进入“状态与证据”页；页面内固定展示“检查规则”下拉框和“检查输入”按钮。系统仅根据已识别的计算机制给出建议值：静态单点 / SCF → `static-scf`，结构优化 → `structure-optimization`，频率 / ZPE → `frequency-zpe`，AIMD → `aimd`，NEB → `neb`；用户仍可改为“基础 VASP 输入”。普通目录不显示该入口。

点击执行时，面板仅对当前任务调用任务级接口，读取 `POSCAR`、`POTCAR`、`INCAR`、`KPOINTS` 及 NEB image 目录所需的最少文件，返回 `inputCheck + rawCheck`。结果立即写回当前会话的 TaskStore，并显示规则名与版本、通过 / 注意 / 未通过、证据、已检查文件和未覆盖范围。`PASS` 固定显示为“通过指定规则检查”，旁边保留“不会提交任务或改写输入”的文字；禁止显示“已就绪”或“可提交”。

接口为 `POST /plugins/dsh-vaspflow/task/{taskId}/input-check?profile_id=...`。`taskId` 只是在本次 DSH 会话中定位已扫描任务的内部编号；请求本身不接受任意路径，因而不会让网页端读取扫描根目录以外的位置。Agent 的 `vasp_check_inputs` 继续保留，以支持它对多目录执行同一检查规则；其结果与面板共享同一 `InputCheck` 数据结构。

批量入口暂不放入首版面板：它需要用户先确认“本批次应使用同一规则”以及处理不同规则任务混杂的情况。该入口应在 B2 的任务表中以“选中任务 → 选择一条规则 → 预览数量与规则 → 执行”的流程出现，而不能简单对当前项目所有目录一键检查。

#### B2. 功能清单

- 批量扫描并展示上述状态、最后更新时间、最后能量、离子步数；
- 按状态、任务类型、路径、修改时间筛选；
- 对一批任务生成“未发现计算输出 / 任务完成 / 检测到错误 / 正在运行 / 待检查”总表；
- 批量检查电子和离子收敛、常见错误签名、输入一致性；
- 导出 CSV/JSON 摘要，方便论文作图或课题组记录；
- 初版项目任务台账：记录任务创建、输入构建、扫描和状态变化等事实事件；
- 批量构建采用“计划 → 确认 → 执行 → 校验”的运行状态，而不是只在结束后返回一段文字；
- 建立批量任务实验板：按体系、构型、吸附物种、位点或参数分组展示任务卡片；文件树仅作为卡片详情中的核查器；
- 建立执行详情视图：展示当前任务的来源文件、文件复制/链接/改写、Selective dynamics 与 INCAR 差异、POTCAR 检查、失败证据及最终产物；
- 大批量时以状态矩阵和聚合计数为主，仅展开当前或被选中的任务，避免把操作事件退化成日志墙。

#### B3. 工作流执行状态

计算任务状态（如 `UNKNOWN`、`ERROR_DETECTED`）与 Agent 的工作流执行状态必须分开建模，避免把“VASP 任务待检查”与“AI 正在构建输入”混为一谈。

| 工作流状态 | 含义 |
|---|---|
| `PLANNING` | 正在生成或校验 dry-run 计划，尚未写入 |
| `WAITING_FOR_CONFIRMATION` | 已发现覆盖、提交或其他需要用户决定的操作 |
| `APPLYING` | 正在执行已确认的真实文件操作 |
| `PAUSE_AFTER_CURRENT_TASK` | 在当前任务边界完成后暂停，避免中途留下不完整任务 |
| `PARTIALLY_FAILED` | 批次继续完成，但有部分任务失败且保留证据 |
| `COMPLETED` / `CANCELLED` | 已完成或在安全边界取消 |

#### B4. 验收场景

1. 给定混合 20 个任务的目录，面板和 Agent 对每个任务给出相同的状态、理由与证据引用；
2. 至少包含：普通目录、未发现计算输出、正在运行、待检查（至少覆盖未结束和已结束未验证两种原因）、任务完成、检测到错误六类样例；
3. 单个目录损坏时，批量巡检仍完成且明确标记该目录；
4. 用户可从“检测到错误”和“待检查”列表直接看到证据文件、关键错误片段或无法判定的原因。
5. 对包含成功、校验失败和覆盖风险的输入构建批次，用户能在写入前看到计划；写入后每个任务的实际文件操作、检查结果和失败原因均可定位；
6. 面板中的构建进度和任务状态必须与 `OperationEvent` 一致；任一状态不得仅由动画或 LLM 文字生成。

**优先级：最高。** 它是 DOS、ZPE、诊断、日志、透明执行工作台与报告面板的共同入口。

### 阶段 C：0.4 — 第一个完整分析闭环：DOS 与 ZPE

**目标：** 不追求同时支持所有 VASP 分析，而是先交付两条可完整验收的工作流：DOS 与 ZPE。

#### C1. DOS / PDOS / d 带中心

**自动化范围：**

- 从已收敛结构优化任务构建静态 SCF 和 DOS 任务；
- 明确复制或链接哪些重启文件，保留原任务不覆盖；
- 对 DOS 所需 INCAR、KPOINTS、`LORBIT` 等进行任务类型校验；
- 解析 DOSCAR / vasprun.xml 中的总态密度和投影态密度；
- 在固定定义、能量零点和积分范围下计算 d 带中心。

**可视化范围：**

- 费米能级对齐；
- 总 DOS、元素/原子/轨道投影 DOS 的筛选与叠加；
- 自旋通道显示；
- d 带中心标记、积分区间与计算定义同屏显示；
- 图片和数据表导出。

**验收要求：** 对一组公开或脱敏参考数据，曲线、费米能级处理和 d 带中心与选定参考实现的差异在预先定义的容差内。不同赝势、非共线、自旋轨道等复杂变体在首版应明确标为“不支持”或“待验证”，不能静默给出数值。

#### C2. ZPE / 频率分析

当前已有 ZPE 输入构建基础，后续补齐：

- 批量识别频率任务及其关联的弛豫任务；
- 解析实频、虚频、ZPE、熵项和自由能贡献；
- 虚频计数与阈值警告；
- 多任务 ZPE/自由能对比表和图；
- 明确温度、标准态与所用公式，避免把不同定义的自由能直接比较。

**验收要求：** 每个 ZPE 数值都可定位到源 OUTCAR 和使用的温度/公式；发现虚频时不能把结果标为“已验证稳定”。

### 阶段 D：0.5 — 结构化汇报、可信诊断与项目记录

**目标：** 让 LLM 成为有依据的项目协作者，而不是替代解析器的聊天窗口。

#### D1. 汇报面板

新增一个“汇报”标签页或独立 dock 区域。它消费受 schema 校验的 `ReportCard`，用于在工作流完成后进行总结；实时执行状态由阶段 B 的任务实验板和执行详情视图承担。它至少支持：

- 任务或批次摘要卡；
- 指标大字报：成功数、失败数、待处理数、关键能量/误差；
- 可折叠表格：任务、状态、证据、文件链接；
- 图表引用：收敛曲线、DOS、COHP、ZPE 对比；
- 文件结构和可点击文件；
- “建议下一步”与“需要用户确认”的明确分区。

首批报告模板：批量输入构建报告、批量巡检报告、失败任务诊断报告、DOS/ZPE 分析报告。每张报告均可回链到相应的 `WorkflowRun`、`OperationEvent` 和 `EvidenceRecord`。

#### D2. 失败任务诊断闭环

```text
确定性解析器识别错误和取证
      ↓
生成 EvidenceRecord（错误签名、文件片段、任务参数）
      ↓
LLM 按证据解释：已知事实 / 可能原因 / 推荐操作 / 风险
      ↓
用户确认后，才创建修复后的输入或提交操作
      ↓
WorkflowRun 与 OperationEvent 记录该次修复和结果
```

首版只覆盖明确、常见且可验证的错误，例如：电子步不收敛、离子步达到上限、`ZBRENT`、`EDDDAV`、`TOO FEW BANDS`、缺少文件和输入冲突。不要在首版自动修改参数；先给出差异化建议和可审阅的修复草案。

#### D3. 项目日志

日志分为两层：

- **事实台账：** 工具自动记录工作流事件，不能由 LLM 编造；
- **可读叙述：** LLM 依据台账生成日报、周报、项目节点总结，可由用户编辑和导出。

建议的事实事件字段：时间、操作者（用户/Agent/工具）、任务或批次、动作、输入摘要、结果、证据引用、是否需确认。对写入型工作流，还要记录关联的计划、来源/目标文件与实际变更。

**验收要求：** 任意一段 LLM 汇报都能回链到任务、数据、文件或规则；没有证据的内容必须显示为“建议/假设”，不能伪装为事实。

### 阶段 E：0.6 — COHP / LOBSTER 联合工作流

**目标：** 支持从 VASP 输入准备到 LOBSTER 后处理和原位解读的第一版闭环。

COHP 不是“再解析一个文件”那么简单，它引入 LOBSTER 兼容性、基组、投影与键对选择。因此应单独建模为 VASP + LOBSTER 工作流。

| 子项 | 首版范围 |
|---|---|
| 输入准备 | 检查 VASP 静态计算是否满足 LOBSTER 所需文件和设置；生成/校验 LOBSTERIN |
| 兼容性检查 | 报告 POTCAR、basis、带数、投影等已知风险；证据不足时明确未知 |
| 结果解析 | COHPCAR、ICOHPLIST 等常见输出的结构化解析 |
| 可视化 | 键对筛选、COHP 曲线、费米能级、成键/反键区间、ICOHP 表 |
| 批量比较 | 多构型/多吸附位点的 ICOHP 对比与导出 |

**验收要求：** 选定的小型参考体系可复现 LOBSTER 结果解析；任何“不支持的 LOBSTER 输出格式”都应明确报错，不得错误画图。

### 阶段 F：0.7 — AIMD、调度器和长任务管理

**目标：** 处理长时间运行、大文件和可续算的任务。该阶段复杂度高，必须在前述任务状态模型成熟后再开始。

范围建议：

- 首先只支持用户实际使用的一种调度器（例如 Slurm 或 PBS），不要同时承诺所有 HPC 环境；
- 读取排队、运行、完成、失败等调度器状态，并与目录扫描证据交叉验证；
- AIMD 输入构建、任务监控、轨迹/温度/能量/压力曲线；
- 大文件增量解析和缓存，避免每次打开面板重读全部 OUTCAR/XDATCAR；
- 续算只生成草案或 dry-run，涉及 `WAVECAR`、`CONTCAR`、提交命令时需用户确认；
- 后续再评估 RDF、MSD、配位数等统计分析。

**验收要求：** 大型轨迹不会阻塞前端；断点续算不覆盖原始任务；调度器不可用时系统能退化为纯文件检查，而不是误判任务状态。

### 阶段 G：1.0 — 研究项目工作台

**目标：** 完成最小但完整的研究闭环。

用户可以在 VASPFlow 内完成：

```text
选择结构和模板
  → 批量构建 / 预览 / 校验
  → 提交前确认与任务巡检
  → 收敛、失败与一致性检查
  → DOS / ZPE / COHP 等结果分析
  → 原位图表、批量比较与证据化汇报
  → 自动事实台账 + 可编辑项目总结
```

1.0 的定义不是“支持所有 VASP 功能”，而是上述闭环在一组真实研究项目中稳定可用、可解释、可回溯。

## 6. 功能优先级矩阵

| 能力 | 用户价值 | 实现/验证成本 | 推荐顺序 | 原因 |
|---|---:|---:|---:|---|
| 批量状态与收敛巡检 | 很高 | 中 | 1 | 所有后续工作流共用，立即减少人工巡检 |
| 透明构建计划与事实事件 | 很高 | 中 | 2 | 是可观察性、诊断、报告和可追溯性的共同底座 |
| 批量任务实验板 | 高 | 中 | 3 | 将真实工作流呈现为可理解的计算实验，而不是目录和日志 |
| DOS/PDOS + d 带中心 | 很高 | 中高 | 4 | 高频且能形成输入—分析—图表的完整闭环 |
| ZPE 解析与批量汇总 | 高 | 中 | 5 | 已有输入构建基础，较容易形成可靠扩展 |
| 报告卡片面板 | 高 | 中 | 6 | 使 LLM 的成果从长文字变为可审阅信息 |
| 失败诊断 | 高 | 中高 | 7 | 必须建立在状态和证据模型上 |
| COHP/LOBSTER | 高 | 高 | 8 | 价值高，但涉及外部软件与兼容性 |
| VASPsol | 中 | 中 | 9 | 输入构建较直接，可穿插在 DOS/ZPE 后 |
| AIMD/HPC 管理 | 很高 | 很高 | 10 | 对基础状态模型、性能和环境依赖要求最高 |

## 7. 测试、验证与科研验收

### 7.1 测试分层

| 层级 | 验证内容 |
|---|---|
| 单元测试 | POSCAR、INCAR、OUTCAR、DOSCAR、COHPCAR 等解析器；状态规则；数值公式 |
| 契约测试 | 每个 `vasp_*` 工具的输入/输出 schema、错误格式和批量容错 |
| 回归测试 | 已经出现过的 SD、POTCAR、模板、路径、安装问题都固化为样例 |
| 集成测试 | 面板、数据服务与 Agent 工具对同一目录给出一致结果 |
| 参考对照 | 与人工核对、VASP 标准输出或选定成熟工具的结果对比 |
| 真实项目试用 | 使用真实但脱敏的课题数据，记录失败案例与用户操作路径 |

### 7.2 每个工作流的完成定义（Definition of Done）

一个新工作流只有同时满足以下条件，才算“支持”：

1. 有明确支持范围、输入前提和不支持项；
2. 可由工具以结构化数据执行或解析；
3. 写入前可 dry-run，写入后可校验；
4. 有至少一组成功样例与一组失败/边界样例；
5. 关键结论能在前端或导出报告中显示来源、单位和参数；
6. Agent 知道何时调用、何时向用户确认、何时拒绝猜测；
7. 文档中有面向新用户的最短使用路径。
8. 若工作流会写入文件，用户可在写入前查看结构化计划、覆盖风险和关键参数差异；写入后可从实际操作事件回链到每项变更；
9. 若工作流有实时展示，所有视觉状态均能对应真实操作事件；暂停、取消和失败的边界行为有测试，不能以模拟进度掩盖未完成操作。

## 8. 需要产品负责人持续决定的事项

以下不是代码能替代的选择，应在进入对应阶段前由项目负责人确定。

| 决策 | 为什么需要你决定 | 建议的默认选择 |
|---|---|---|
| 首批真实研究场景 | 决定 DOS、ZPE、COHP 的优先级和验收数据 | 选择你当前课题中最常出现的一条流程 |
| 任务类型定义 | 同一名称在不同课题组的 INCAR 习惯可能不同 | 首版只固化自己的可靠模板，并明确前提 |
| d 带中心/ZPE 的公式与报告口径 | 属于科研方法选择，不是纯软件选择 | 在文档和报告中固定公式、能量零点、温度和单位 |
| 调度器优先级 | HPC 环境差异很大 | 先支持你实际使用的一种调度器 |
| 自动修复权限 | 会直接影响计算资源和科研数据 | 首版只建议和生成 dry-run；用户确认后才写入/提交 |
| 样例数据授权 | 真实数据最能验证工具，但可能敏感 | 维护一套可公开脱敏的回归数据集 |

## 9. 下一开发周期的具体任务清单

下一周期聚焦透明构建基础与 `0.3` 的任务巡检，不同时启动 DOS、COHP 或 AIMD。

1. 为批量输入构建定义 `BuildPlan`、`WorkflowRun`、`OperationEvent` 的 schema 与最小持久化方式；
2. 扩展 dry-run，使其输出逐任务的来源、目标、文件操作、Selective dynamics / INCAR 差异、POTCAR 检查与覆盖风险；
3. 为真实写入接入操作事件记录，并验证计划与实际结果的一致性；
4. 定义并实现统一计算任务状态与证据字段；
5. 扩展扫描/OUTCAR 解析，使其能输出状态、原因和最后更新时间；
6. 做批量状态汇总、筛选、失败列表和首个任务实验板；
7. 为普通目录、VASP 任务目录、五类任务状态及构建中的成功、部分失败、覆盖风险建立最小回归样例；
8. 在 Agent 中加入“先生成计划—说明影响—确认后执行—引用证据汇报”的工具使用协议；
9. 在面板中实现首个构建执行详情和批量巡检视图；在工作流完成后再生成首个 `ReportCard` 原型；
10. 用一个真实小项目验收，记录误判、未知状态、计划与实际不一致以及性能问题。

完成上述七项后，再进入 DOS/ZPE 闭环。这样做能避免为每一种计算类型各写一套扫描、诊断和报告逻辑。

## 10. 路线图成功指标

不以“工具数量”作为主要成功指标，而以实际研究工作是否更可靠、更省时来衡量。

| 阶段 | 建议指标 |
|---|---|
| 0.3 | 真实批次中的任务状态人工复核一致率；每次巡检节省的人工时间；未知/误判任务比例；用户能否在不阅读终端日志的情况下回答“AI 改了什么、为什么改、哪些任务异常” |
| 0.4 | DOS/ZPE 工作流从构建到图表的人工步骤数；参考数据数值一致性；用户是否仍需手动搬文件 |
| 0.5 | 每份诊断是否有证据引用；用户采纳建议后的成功率；项目日志是否可用于复盘 |
| 0.6–0.7 | COHP/AIMD 真实项目完成率；大文件处理性能；续算和调度器状态的错误率 |
| 1.0 | 一个研究项目从建模到结果汇报能否主要在 VASPFlow 内完成；用户是否愿意连续使用 |

## 11. 核心取舍

- **先做透明构建和任务巡检，后做更多输入生成器。** 输入生成器很容易增加；统一状态、计划、事实事件和验收能力才会让它们真正可用。
- **先做 DOS/ZPE，后做 COHP/AIMD。** 前两者与当前能力衔接更好、验证边界更清楚。
- **先做真实执行可视化，后做“自由的 LLM 可视化”。** 运行中的任务实验板由真实事件驱动；完成后的结构化卡片可验证、可复用、可保证事实来源。
- **先做诊断建议，后做自动修复和自动提交。** 科研计算的资源消耗和数据风险决定了这一顺序。
- **不做模拟电脑操作。** 不以逐字输出、虚构鼠标路径或装饰动画替代真实操作证据；正常批量工作也不要求用户全程盯守。

这条路线的最终价值不在于“VASPFlow 会多少命令”，而在于它能把一次 VASP 研究工作从输入、执行、检查、分析到汇报，组织成一个可信、清楚、可追溯、可观察的过程。
